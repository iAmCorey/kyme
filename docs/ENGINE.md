# 引擎：组句和纠错

`kyme-pinyin` 把打的一串字母变成首选整句和候选。难点在纠错：手误要纠得回来，打对的拼音一个字母都不能改。这篇讲为什么是现在这套做法。代码在 `crates/kyme-pinyin/src/engine.rs`，检查方法见 [QA.md](QA.md#照着打的拼音不能被改)。

## 显示和理解

- **输入框显示打的字母**：`Conversion.preedit` 永远是打的字母。纠过错的词照原样显示，词里不插分隔符，比如 `zhnog` 显示 `zhnog`；回车上屏的也是这些字母。
- **理解记在 spelling**：引擎把输入理解成什么，记在 `spelling` 里，比如 `zhnog` 是 `zhong`。下面说的「改掉」，都是指 `spelling` 和打的字母不一样。

## 组句

在词图上找代价最小的一条路（Viterbi，动态规划求最短路）：

- **词的代价**：每个词是 −ln(词频 / 总词频)，再加 `WORD_PENALTY`（1.5），让引擎偏向长词。
- **切法的惩罚**：切法本身也有惩罚，比如简拼、没打完的末尾音节、各类纠错。
- **看搭配**：只看词频的话，`haonanhe` 出「好难和」，因为「和」比「喝」常用得多。所以组句时再看相邻两个词接得顺不顺：前一个词的最后一个字和后一个词的第一个字，在词库的词里挨着出现得多不多（含这一对字的词，词频加起来）。按次数取对数连续地罚，次数越少罚得越重，十万次以上不罚，一次都没有罚约 2.3。「难喝」是词、「难和」几乎没有，就出「好难喝」。代码在 `pairs.rs`。
- **搭配只换字**：首选的读音（纠过错的是纠正后的）定下来以后，只在这串音节上再排一遍，这回算上搭配，换成排第一的那句，原来的首选排第二。要不要纠错照旧只比词频，所以打对的拼音不会因为搭配被改。
- **不看光标前的文字**：「夜市吃点」后面的 `meishi` 该是「美食」，这类要靠前文才分得清的留给 AI 组句（[PLAN.md](PLAN.md)）。

## 本地词库和用户词

- **本地词库**：自定义词库和导入的外部词库，和主词库共用音节表和总词频，代价能直接比，加了词也不改变主词库的代价。没写拼音的词切成主词库里的词补读音（取代价最小的切法，整词有就用整词）；写了拼音但音节没隔开的按字数切开，切法不止一种时挑和每个字的读音对得上的（「西安」写成 `xian` 是 xi an）；没写词频按 10000 算，外部词库的词一律按中位数 500。
- **扩展词库**：雾凇的扩展词库和腾讯词库，在设置窗口里下载、打开后才载入。每个文件单独一层，和本地词库一样只进照着打的读法；各层各自重建、互不覆盖，关掉一个直接卸掉，不用重建别的。腾讯词库只写了词和词频，载入时按主词库补读音：近百万个词按文字查主词库，用一张常驻的开放寻址表（主词库约 4MB，第一次用到时建）查，约 1.4 秒；用二分查找要 5 秒。
- **建词库时压低内存峰值**：释放的内存不一定还给系统，常驻内存基本等于构建时最高的那一刻。所以排序不缓存 key，补读音查的是常驻的小表、不临时建大表（临时建的话，自定义词库里有一个没写拼音的词，每次重建就多占 25MB），几层词库一个接一个地建。腾讯词库这一层因此从多占 109MB 降到约 65MB，输入法默认设置下的常驻内存也从 128MB 降到 120MB 左右。
- **常选的词加分**：用户主动选过的词，代价减去 `min(6, 2.5·ln(1+次数))`，次数每 60 天减半；分几次选出来的词组记成新词，从词库词频的中位数起算。每段取前 3 个词时，本地词、用户词和主词库的词一起排，同一个词留代价低的，主词库里排在后面的词常选也能进来。
- **只进照着打的读法**：纠错的读法只用主词库，所以本地词和用户词只会让照着打的读法更占优，打对的拼音更不会被改。评测带上一万个故意捣乱的本地词和一万个用户词再跑一遍，被改的不能变多。

## 纠错的种类

| 手误 | 例子 | 惩罚 |
|---|---|---|
| 相邻打反 | `zhnog` → 中 | 2.5 |
| 跨音节打反 | `nhiao` → 你好 | 3.0 |
| 漏字母 | `zhngguo` → 中国 | 3.0 |
| 按错相邻键 | `zhonf` → 中 | 4.0 |
| 连按两次 | `nihhao` → 你好，`womenndou` → 我们都 | 2.0 |

- **一个词里最多纠一处**：两处都错的情况很少，放开的话切法会成倍增加。
- **最后一个字母不算多按**：它更可能是下一个音节的开头，比如 `zhongg` 是还没打完的 `zhongguo`。
- **没有元音就不纠错**：一个元音都没有的输入按简拼处理，比如 `rgzn` → 人工智能。

## 问题：纠错太容易赢

纠错常常把两个音节并成一个，整句少一个字，代价也跟着少一截。只调每一类的惩罚，压不住它：

- `naan` 照着打是 `na'an`「那按」，纠成 `nan`「难」只好 5.3，这时不该改。
- `xiaang` 纠成 `xiang`「想」，比照着打的 `xia'ang`「下昂」好 10.6，这时要纠。

两条要求的方向相反，同一个惩罚怎么调都会顾此失彼。

## 做法：和「照着打」的读法比

```
convert(输入)
  ├─ 一个元音都没有 ────────────────────→ 按简拼读（Plain）
  ├─ 允许纠错时的最优整句没用到纠错 ────→ 直接用
  ├─ 纠错整句的代价 + 7 < 照着打的代价 ─→ 用纠错整句
  └─ 其余情况 ─────────────────────────→ 按不纠错的读法（Plain）
                                          纠错改的是没打完的末尾音节时，纠错整句排第二
```

- **照着打（Literal）**：只认打全了的音节，最后一个可以没打完，不含简拼，也不含纠错。它就是「用户照着打」的那种读法。
- **门槛**：`TYPO_MARGIN = 7`，夹在上面的 5.3 和 10.6 之间。所以 `naanni` 出「那按你」，`xiaang` 照样纠成「想」。

## 末尾没打完的音节

最后一个音节没打完时，分不清是还没打完，还是最后一下按错了。比如 `suho` 可能还要接着打成 `suhong`，也可能是「说」打反了。

- **首选按照着打的读法，纠错结果排第二，按 2 就能选**：`suho` 出「苏红」「说」，`dianyinf` 出「点印发」「电影」。
- **打完整的音节少往长里猜**：末尾已经是完整音节时，按更长的音节联想罚 6.0，`meine` 是「没呢」，不把 `ne` 联想成 `neng` 出「没能」。判断要不要纠错时，照着打的读法仍罚 4.0：罚重了它就变贵，纠错更容易赢，打对的拼音更容易被改（试过都用 6.0，常用拼接被改的从 0.12% 涨到 0.14%）。
- **末尾也用 7，不放宽**：打到一半是每按一个键都会经过的状态。试过放宽，常用音节拼接里大约 3% 会在打字过程中首选来回变：打到 `lain` 读成 `lian`，再打一个 `a` 又变回 `lai'na`。

## 一串字母能切成几种读法

`wengan` 可以是 `weng'an`「瓮安」，也可以是 `wen'gan`「温感」；`xian` 可以是「先」，也可以是 `xi'an`「西安」。首选按词频挑一种，另一种也要选得到：

- **别的切法的字也进候选**：首选以外的候选，原来只收结束在首选切分边界上的词。`wengan` 的首选是 `weng'an`，「温」只占 `wen` 三个字母，就被挡掉了，选都没得选。现在全是打全了的音节的词也可以结束在别处，只要剩下的字母照着打读得通；`kaihui` 仍不出「开户」，因为会剩下打不出来的 `i`。
- **每种长度各有上限**：候选按覆盖的字母从长到短排。原来整张表最多 60 个，`jia` 能往下联想成 `jian`、`jiang`、`jiao`，光是这一长度的字就占满了，`ji'a` 的「机」排不进来。现在每种长度各 60 个。
- **生僻字排在后面**：词频低于 1000 的单字（自带词库里约四成）排在所有常用的字词后面。不然 `wengan` 的「温」要排在 `weng` 的「蓊、𬭩、滃」后面，到第二页才有。
- **打全了的音节不拆成简拼**：简拼的字母如果能和后面的字母拼成完整的音节（`shuo` 的 `s`），或者是前一个音节的最后一个字母（`jian` 的 `n`），就不按简拼读。原来 `duishuo` 读成 `dui's'huo`「对生活」，`jianda` 读成 `jia'n'da`「加拿大」，最常用的 150 个音节两两拼接里有 162 个这样。拼不成音节的字母照样按简拼读（`nhao` → 你好，`zgr` → 中国人），元音开头的简拼（`eq` → 而且）也不受影响。

切法本身的选择还是只看词频：`zhengeng` 首选是 `zheng'eng`「正嗯」，因为「嗯」在词库里同时登记了 `en` 和 `eng`，词频又极高。`zhen'geng` 选得到，但不在第一页。

## 取舍

- **末尾打错时首选不是纠错结果**：最后一个音节打错时，首选是照着打的读法，纠错结果排第二。要让它排第一，得有能看上下文的组句。这两条用例放在 `eval/pending.tsv`。
- **少数明显的手误仍会被改**：`ow` 这种纠错明显更合理的输入，还是会改成 `wo`「我」。这类算在门槛允许的 0.5% 里。

## 搭配的参数怎么定的

从词库里拿掉 3304 个三四个字的常用短语，看引擎能不能用剩下的词把它们拼出来：

- **不看搭配**：拼对 47.2%。
- **看搭配**：拼对 51.7%，修好 227 个，改坏 81 个。改坏的多是对的那句搭配在词库里没出现过，比如「被法院」拼成了「备法院」：词库是词表不是语料，没出现过不等于接不上。
- **按次数连续地罚**：最早是到 100 次就不罚，没出现过的一律重罚，结果冷门词「点九图」让「点九」算常见，`youdianjiujie` 成了「有点九节」。改成按次数取对数连续地罚，系数 0.2：再大「有点纠结」就要翻，再小「好难喝」又翻不过来，两条都留着 0.25 左右的余量。
- **别的算法**：按含这一对字的词数算、只数三个字以上的词，结果都差不多，所以不搞复杂。

## 试过、没用的做法

- **逐类调惩罚**：调好了一类，另一类就坏，比如上面 `naan` 和 `xiaang` 的冲突。
- **跨音节连按罚得更重**：`DOUBLED_ACROSS_PENALTY` 罚到 3.0 就纠不回 `womenndou` 了，所以和同一个音节里连按一样，罚 2.0。
- **末尾从宽**：首选会在打字过程中来回变，见上一节。

## 改引擎之前

```bash
cargo xtask qa --only eval,scenarios
```

- **评测集要全对**：`eval/pinyin.tsv` 的每一条首选都要对，从第一个字母打到最后一个，每一步的 `preedit` 都是打的字母。「本来就对」那一类每一步的 `spelling` 也不能变。
- **常用拼接的门槛**：最常用的 80 个音节两两拼接，被改掉的比例不能超过 `qa/gates.toml` 里的 `max_altered_percent`。
- **每种读法都选得到**：最常用的 150 个音节两两拼接，想打的读法都要选得到，首选也不能把打全了的音节拆成简拼。
- **做不到的先挂着**：暂时做不到的用例放进 `eval/pending.tsv`，只报告，不卡发版。
